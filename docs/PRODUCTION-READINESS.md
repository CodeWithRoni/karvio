# Production hardening — prepared release

Baseline: main 944cf5589ad7d3a76d06536dad55214d955f8f83, hosted Edge v57. Owner authorized publication of this prepared patch. The checks below describe the prepared release; GitHub Actions records rollout completion. No historical business-row rewrite or native release is requested.

## Implemented and locally verified

- Five wrong administrator confirmations lock the initiating user's confirmation attempts for 15 minutes. Counts persist even when the financial operation fails. Correct-password attempts during lockout are rejected; another admin remains independent. New/password-reset credentials require 12 characters; existing credentials keep working until changed.
- Deployment graph: test/build -> migrations -> backend deployment -> exact commit/build ID verification -> publish tested frontend artifact. Missing credentials or backend failure blocks frontend publication. Active deployments are not cancelled halfway by a new push.
- Protocol 2 commits send only changed rows/deleted identifiers, preserving historical rows that did not change. All rows of a table are no longer deleted on a normal sale. Row-position shifts during a genuine deletion/restore can still affect multiple rows. Snapshot, optimistic revision check, money changes, receipt/idempotency metadata and SMS outbox remain atomic.
- Runtime uses copy-on-write instead of deep-copying the complete sheet state before every action. Protocol 2 derives deltas without converting every unchanged historical row back into a database record.
- Ping uses a lightweight status RPC. Login/logout/users.list/sms.log/expenses.list use explicitly scoped snapshots; a missing dependency fails rather than being treated as an empty business table.
- Request limits are independent of forwarding headers. Stored unexpired sessions identify the user bucket (180 requests/minute); invalid/random sessions share an anonymous bucket (180/minute); the shop-wide ceiling is 900/minute. These are gateway limits, not a replacement for confirmation/login lockouts. Tune only after representative load tests. Shared anonymous limits can affect a busy public invoice audience; this is a deliberate bounded fallback without a trusted-IP contract.
- Daily retention now covers all snapshot reasons, not only scheduled backups, while preserving at least the newest ten recovery points. Retention defaults to 30 days, bounded to 1..365. Pruning runs via the existing daily job, including when new scheduled snapshots are disabled.
- Four deferred foreign keys protect invoice/return parent-child references. Migration validates existing rows and stops on orphaned data; it never silently deletes or repairs financial records.
- Version strings aligned to 1.2.3 and deployment verifies build ID rather than version alone. Removed legacy Sheet ID/duplicate backend parts. Tauri CSP is explicit; it still permits HTTPS API endpoints and inline styles needed by the existing UI.

## Important remaining work — do not claim full scale readiness

1. Transactions, bootstrap, broad reports and many other actions still load a complete snapshot. The large-data CPU/memory problem is reduced, not eliminated. Porting these to bounded action-specific queries/aggregates requires a dedicated persistence/business-query migration and compatibility tests.
2. Global runtime row/revision serialization remains. It protects cross-table balances, stock, session state and replay receipts. Removing it without replacing those invariants would introduce overselling/lost updates. Two concurrent sales and a 10,000-row delta fixture pass locally, but this is not multi-device production load certification. Per-resource locking/idempotency and representative stress tests remain.
3. Date and JSON business columns remain text to preserve existing exports/engine compatibility. Four foreign keys do not constitute full normalization. Native date/JSONB conversion and remaining optional-reference constraints need an explicit preflight/data migration plan, not an in-place blind cast.
4. Owner selected Google Drive. A private, unshared Karvio backups folder was created and read back. A checksum-verified 29-table recovery export was prepared locally from a read-only snapshot. After explicit owner approval, the complete backup was uploaded to that private folder. Metadata confirmed it is unshared; a complete download matched the local 75,813-byte file byte-for-byte. Evidence and private file link are kept in local verification/production-fixes/drive-status.json. This is one recovery copy, not a scheduled backup. Server-side Google authorization/upload scheduling are not configured, so off-project automation is NOT active. The chat's Drive connection is not a persistent server credential. Current snapshots remain in the Supabase project; existing manual database exports remain available.
5. Tauri configuration was validated, not a signed/native Tauri installer on physical devices. The current released desktop workflow uses Electron.

## Publication procedure (only after explicit owner push instruction)

Review the two new migrations in order. Preflight existing orphan rows before applying. The workflow runs pending migrations before Edge; requires a Supabase token with database migration rights in addition to function deployment rights. PostgreSQL migrations passed PGlite tests and a rehearsal using a de-identified 29-table/609-row recovery copy. All existing business rows were preserved, scoped reads and a sale/cancellation passed, and live orphan preflight counts were zero. This is not large-scale production load certification.

Do not mix a deployed protocol 2 Edge with a database lacking karvio_status, karvio_snapshot_for, karvio_request_limit or karvio_commit_delta. Keep the old commit RPC for rollback compatibility. Apply migration -> deploy backend -> verify exact build ID -> publish frontend. Do not drop the old RPC or change historical transaction values as part of rollout.
